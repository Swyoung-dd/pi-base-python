# 设计思想

本文记录 piY 当前实现背后的主要设计选择。它既用于解释“为什么这样写”，也用于约束
后续演进，避免局部功能破坏整体边界。

## 1. 统一语义，隔离协议差异

Agent 不应理解 OpenAI、Anthropic 或其他厂商的请求格式。`pi.ai` 先定义统一的模型、
消息、工具和事件语义，provider 只在边界完成双向转换。

这样做的收益是 agent 循环只实现一次，provider 可以独立测试和替换。代价是公共类型
必须表达各 provider 的有效交集，并为思考签名、缓存用量等差异保留显式字段。

演进约束：新增 provider 特性时，先判断它是可复用的领域概念还是厂商私有细节。前者
进入公共类型，后者留在 provider 内部，避免公共模型退化成任意字典。

## 2. 用事件流贯穿整个调用链

模型输出天然是增量的，工具执行和重试也具有生命周期。piY 使用结构化事件连接 provider、
agent、TUI、SDK 和 RPC，而不是让底层直接打印文本。

收益包括：

- TUI 可以即时渲染文本和思考过程。
- SDK 可以订阅同一套事件而不依赖终端。
- 工具开始、结束、重试、压缩和整轮结束都有稳定的观测点。
- 测试可以断言事件顺序和状态转换。

演进约束：新增用户可观察行为时，优先扩展类型化事件，并保持事件顺序可预测；不要在
agent 内核中直接进行界面输出。

## 3. 分离循环机制与长期状态

`run_agent_loop()` 处理一次模型与工具的反馈循环，`Agent` 管理跨轮次状态和外部控制。
循环接收上下文快照、函数和事件 sink，而不是依赖全局单例。

这使核心机制容易注入假的 provider 和工具进行测试，也让会话存储、steering、follow-up
和取消保持在清晰的状态边界内。

演进约束：纯粹的单轮控制逻辑放入 agent loop；需要跨轮次保留或被客户端控制的能力
放入 `Agent`；特定编码产品的资源装配留在 `coding_agent`。

## 4. 组合优先于隐藏式自动发现

运行时在单一组合根中显式创建内置工具、加载扩展并拼接提示。Python entry point 扩展
默认关闭，只有配置明确启用后才发现。

显式组合让能力清单、冲突检测、启动失败和安全审计更容易理解。扩展可以增加工具、模型、
provider、命令和事件处理器，但不需要修改核心循环。

演进约束：新增运行时资源应接入 `build_runtime_resources()` 或其清晰的下层接口；避免
模块导入时产生不可见的项目级副作用。

## 5. 持久化采用只追加事件，而非覆盖快照

会话以 JSONL 条目持续追加，并通过父节点表达分支。模型切换和上下文压缩也是一等会话
事件，而不仅是内存状态。

这种设计便于恢复、审计和分支，也能通过容忍末尾残缺记录应对意外中断。代价是读取时
需要重建当前分支，长期会话文件也会增长。

演进约束：不要原地改写历史条目。需要表达新状态时增加条目类型，并保证旧记录仍可被
读取；引入格式变更时应同时考虑版本迁移策略。

## 6. 上下文是有限资源，需要可恢复地降级

上下文压缩优先保留近期完整交互，用模型摘要保存早期目标、决策与进度。摘要调用失败时，
确定性压缩保证主流程不因辅助能力失败而中断。

Skill 也采用渐进披露：常驻提示只包含元数据，正文按需读取。这两种机制共同控制 token
开销，而不是无限累积提示内容。

演进约束：任何常驻系统提示、工具描述和自动注入内容都要计入上下文成本；新增内容时应
说明其长期驻留的必要性。

## 7. 默认并发，但保持结果顺序确定

同一助手消息中的多个工具调用默认并行执行，以降低互不依赖任务的总延迟。结果通过与原始
调用顺序配对后回填，使模型看到的上下文稳定。需要顺序副作用时可以切换为串行模式。

演进约束：工具实现不能假定同轮其他工具已经完成。具有共享可变状态或先后依赖的调用，
应由调用者明确串行化，或在工具内部实现同步。

## 8. 错误应结构化并尽量局部隔离

未知工具、工具异常和取消会转换为 `AgentToolResult`；provider 错误形成终止消息；扩展
生命周期处理器的异常被收集为 `ExtensionFailure`，不会阻止其他处理器运行；压缩失败有
确定性回退。

这里的目标不是吞掉错误，而是让错误沿着既有协议可见，同时控制影响范围。

演进约束：保留错误上下文和 `is_error` 等机器可读信息。只有存在明确恢复策略时才捕获
异常，不能用宽泛捕获掩盖状态损坏。

## 9. 信任决策与能力限制是两件事

项目信任解决的是“是否加载仓库提供的可执行或注入型资源”，不是“agent 可以访问什么”。
目前工具仍运行在宿主进程权限下，因此调用方必须根据使用场景补充沙箱、目录约束、命令
审批或凭据隔离。

演进约束：安全文档和界面必须准确描述实际边界。未来增加权限系统时，应在工具执行入口
形成统一策略，而不是让每个 UI 各自实现不一致的检查。

## 10. 跨平台行为在边界处适配

核心 agent 逻辑不区分操作系统。命令工具在 Windows 选择 PowerShell，在 macOS/Linux
选择 bash，并允许调用者显式选择 shell。CI 同时覆盖三种操作系统和 Python 3.12/3.13。

演进约束：平台差异应封装在工具或适配层；测试和文档命令不能默认所有用户都处于 POSIX
环境。

## 11. 决策检查清单

提交重要设计变更前，应回答：

1. 变更属于 LLM 抽象、Agent 内核、编码场景还是界面层？
2. 是否引入了反向依赖或重复的运行时装配？
3. 新状态是否可持久恢复，新事件是否可被 SDK/RPC 观察？
4. 是否增加常驻上下文、并发副作用或新的宿主权限？
5. 失败时是可恢复、可见并且可测试的吗？
6. 是否需要同步更新公共文档、模型目录或跨平台测试？
